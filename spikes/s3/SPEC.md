# S3: copy-on-write store clones per probe

**Question.** Can each probe item get its own copy-on-write clone of a memory store, cheaply and in isolation, including parallel per-worker sandbox roots?

## Method
- **Fixture stores,** generated by a script with synthetic content:
  - a store shaped like a Hermes home with native memory: memory markdown files, a SQLite state database in WAL mode, and session files;
  - a generic plug-in store: a SQLite database plus a directory of blobs.

  Each comes in sizes of about 10 MB and 100 MB, and one of about 400 MB. Peak extra disk stays under 0.5 GB.
- **Clone after a clean exit,** with APFS `clonefile` (for example `cp -c`). Other platforms, reflink and the SQLite backup API, are noted but not run.
- **Per probe, 20 probes per store:**
  1. clone A is made, and a nonce is written into it, both as a SQLite row and as appended text in a file;
  2. clone B is made fresh from the original;
  3. checks: the original's tree hash is unchanged; the nonce is absent from clone B, by a byte search; no clone contains the original's absolute path.
- **Parallel roots.** N workers, each owning its own sandbox root, run clone, write and verify in a loop. Throughput is measured at 1 and 2 workers, and at 4 and 8 workers only while the machine is idle. If the machine is not idle during the spike, the 4- and 8-worker runs are left as a script and marked deferred.

## Done when
`spikes/s3/REPORT.md` gives clone time by store size (p50, p95), the isolation checks' results for every probe, and probe throughput per hour at each worker count measured.

## Does not prove
- Behaviour with a live daemon holding the store open: snapshots are taken after a clean exit, and daemons need `quiesce()` and `resume()`, which are designed per system.
- Any real memory system's store layout beyond the shapes above. Each system's declared state paths are checked when it is onboarded.
